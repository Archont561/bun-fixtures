## Why bun-test-utils?

`bun:test` is blazing fast, but test setup in complex projects quickly degenerates into brittle `beforeEach` chains, duplicated boilerplate, and leaky teardown state.

`bun-test-utils` brings **pytest-style dependency injection** to `bun test`:

```ts
// test.ts
import { test as base } from "bun-test-utils";

export const test = base.extend({
  db: { scope: "file", setup: async (use) => { await use(await createDb()); } },
  user: { setup: async (use, { db }) => { await use(await db.insertUser("ada")); } },
});
```

```ts
// user.test.ts
import { expect } from "bun-test-utils";
import { test } from "./test";

test("creates and verifies a user", async ({ db, user }) => {
  expect(await db.find(user.id)).toMatchObject({ name: "ada" });
});
```

No manual wiring, no global mocks, and no implicit fixture discovery. `fixtures.ts` and `conftest.ts` are not automatically loaded; fixtures are available only through the imported `test.extend()` chain. `db` and `user` are built in topological order, injected into tests, and cleanly destroyed in reverse (LIFO) order.

## Core Capabilities

<div class="feature-grid">
  <div class="feature-card">
    <h3>⏱️ Scoped Lifecycles</h3>
    <p>Declare fixtures at <code>session</code>, <code>file</code>, or <code>test</code> scope. Long-lived dependencies are cached and shared; short-lived ones reset per test.</p>
  </div>

  <div class="feature-card">
    <h3>🧩 Explicit Composition</h3>
    <p>Compose fixtures with <code>test.extend()</code> and import that runner. Directories never contribute fixtures implicitly.</p>
  </div>

  <div class="feature-card">
    <h3>🔄 Guaranteed LIFO Teardown</h3>
    <p>One setup function handles both preparation and teardown via <code>await use(val)</code>. Cleanup is guaranteed even when test assertions fail.</p>
  </div>

  <div class="feature-card">
    <h3>✖️ Parameterized Tests</h3>
    <p>Express value matrices with <code>test.prop</code> and <code>fc.constantFrom</code>; every sample gets its own fixture lifecycle.</p>
  </div>

  <div class="feature-card">
    <h3>🛡️ Fail-Fast Validation</h3>
    <p>Dependency cycles, missing fixtures, and lifetime scope violations are caught during test collection before any assertion executes.</p>
  </div>

  <div class="feature-card">
    <h3>📦 Built-in Capabilities</h3>
    <p>Use one import: <code>describe</code>, <code>test</code>, and <code>expect</code>. Standard, DOM, browser/server, VCR, and snapshot capabilities live on the root <code>test</code> context; optional property and scenario styles live on <code>test.*</code> after their peers are installed.</p>
  </div>
</div>

## Stability

The fixture engine plus standard, DOM, snapshot, property-testing, and minimal
VCR capabilities are stable. Browser and BDD are experimental and may change in
minor versions. Linux and macOS are supported; Windows support is planned after
the first release. See the [API reference](/bun-test-utils/reference/api/#stability-and-platforms)
for the compatibility boundaries.

## Quick Setup

Initialize your repository in one command:

```bash
bun add -d bun-test-utils
bunx test-utils init
```

This updates your `bunfig.toml` preload configuration. Create a local `test.ts` and compose fixtures explicitly:

```ts
// test.ts
import { test as base } from "bun-test-utils";

export const test = base.extend({
  db: {
    scope: "file",
    setup: async (use) => {
      const db = await createDatabase();
      await use(db);
      await db.close(); // teardown runs here!
    },
  },
});
```
